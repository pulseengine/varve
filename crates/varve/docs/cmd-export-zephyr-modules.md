# export-zephyr-modules — Zephyr modules your build adds, verified

varve carries the Zephyr modules a project **adds**, never Zephyr itself. A
`zephyr-module` payload is the module's source tree, stored exactly as its
producer published it. `export-zephyr-modules` lays each one out and writes the
CMake script that puts them on your build's module path.

```sh
varve export-zephyr-modules --out ./zephyr-modules
varve export-zephyr-modules --out ./zephyr-modules --select gale
```

```
exported 2 zephyr module(s) to /w/zephyr-modules — 6 file(s)
  gale   /w/zephyr-modules/gale
  hal_x  /w/zephyr-modules/hal_x
wrote /w/zephyr-modules/zephyr-extra-modules.cmake — it appends them to ZEPHYR_EXTRA_MODULES; your west.yml is untouched.
  west build ... -- -C /w/zephyr-modules/zephyr-extra-modules.cmake
  or, in a plain CMake build:  include("/w/zephyr-modules/zephyr-extra-modules.cmake")
stamped /w/zephyr-modules/.varve-export.json — export bound to layer 2026.11.0 (sha256:…); `varve verify --export /w/zephyr-modules` checks it
```

## What it writes

```
zephyr-modules/
├── zephyr-extra-modules.cmake
├── gale/
│   ├── zephyr/module.yml
│   └── …
└── hal_x/
    └── …
```

Each module goes to `<out>/<module-name>/`, the tree as stored. The name is the
`name:` in the module's `zephyr/module.yml`, or the payload's own name when it
has none. A name that is not a plain directory component (`..`, `a/b`, a leading
`.`) is refused.

The script **appends** each module's absolute directory to
`ZEPHYR_EXTRA_MODULES`:

```cmake
# Generated by `varve export-zephyr-modules`. Do not edit; re-run the command.
# Layer: 2026.11.0
# Manifest digest: sha256:…
list(APPEND ZEPHYR_EXTRA_MODULES "/w/zephyr-modules/gale")
list(APPEND ZEPHYR_EXTRA_MODULES "/w/zephyr-modules/hal_x")
list(REMOVE_DUPLICATES ZEPHYR_EXTRA_MODULES)
set(ZEPHYR_EXTRA_MODULES "${ZEPHYR_EXTRA_MODULES}" CACHE STRING "…" FORCE)
```

It works both ways Zephyr users reach for. `include()` runs it as ordinary
CMake. `west build ... -- -C <script>` runs it as an **initial-cache script**,
where a plain `list(APPEND)` never reaches the project — only a cache entry
does — which is why the last line is there. Modules you passed yourself with
`-DZEPHYR_EXTRA_MODULES=…` are kept. Paths are quoted for CMake; a path
containing `;` is refused, because a list element with `;` reads back as two.

**Your `west.yml` is never read or written.**

## Declaring it

```toml
manifest-version = 1

[toolchain]
channel = "qualified"
layer   = "2026.11.0"

[[export]]
kind = "zephyr-module"
out  = "zephyr-modules"
```

`varve verify` then checks the directory on every run: one flipped byte in an
exported module fails it, and so does a missing directory.

## What it refuses

- **A pin that carries no `zephyr-module`.** The message says which kind is
  missing and from which layer.
- **An unknown `--select`.** The message lists what the layer does carry.
- **An incomplete `build: depends` closure.** If a module's `module.yml`
  declares `build: depends: [other]` and `other` is not among the modules being
  exported, the export is refused naming both, and **nothing is written**. A
  half export would pass `verify --export` while being incomplete. Narrowing
  `--select` past a dependency is the same refusal.
- **A symlink in a module tree**, and a member path that leaves the tree.
- **Members that differ only in case** (`zephyr/Module.yml` beside
  `zephyr/module.yml`), and a `zephyr/module.yaml` beside the parsed
  description. On a case-insensitive file system one would overwrite the other
  at export, replacing the checked description with an unchecked one. Refused at
  deposit.
- **A `<out>/<name>/` varve did not write.** An export replaces a module
  directory only when `<out>` carries a `zephyr-module` stamp listing files
  under it; otherwise it refuses (`exists and was not written by varve
  export-zephyr-modules; remove it or choose another --out`) before writing or
  deleting anything, so a checkout of your own is never removed.

### What it does not check yet

It does not compare module names against a west workspace's own modules (Zephyr
silently lets the later one win), and a module that depends on one the
workspace's `west.yml` already provides is refused rather than recognised. Both
belong with the `--override` work in REQ-ZMODEXPORT-002. It does not build
anything: the offline Zephyr build against an exported module is not yet proven
end to end.

## Depositing a module

```toml
layer   = "2026.11.0"
channel = "qualified"
counter = 1

[[tool]]
name    = "gale"
version = "0.1.0"
kind    = "zephyr-module"
path    = "gale-0.1.0.tar.gz"
```

The archive is a gzip-tar of the module tree. **The deposit refuses a tree with
no `zephyr/module.yml`, or one that does not parse** — a tree without one is not
a module and would install, verify and then be ignored by every build. The file
sits at the archive root, or inside a single wrapper directory (which the export
strips).

In a realm's `layer.toml` the entry takes `layout = "zephyr-module"` and an
`asset` template, with no `%T`: source is the same on every platform.

## No Python

Neither the deposit nor the export runs Python or needs it. `module.yml` is
parsed in Rust.

A module whose `module.yml` declares `package-managers: pip` adds a Python
dependency to **every build that uses it**. varve distributes the blocks a
project adds, never the interpreter or its packages, so the deposit refuses such
a module unless the layer records an opt-in naming exactly the declared files:

```toml
layer   = "2026.11.0"
channel = "qualified"
counter = 1

[[tool]]
name       = "py-module"
version    = "0.1.0"
kind       = "zephyr-module"
path       = "py-module-0.1.0.tar.gz"
allow-pip  = ["scripts/requirements.txt"]
```

The list must match the `requirement-files` the module declares, as a set. A
different list is a different dependency than the one the operator accepted, so
it is refused too, as is an opt-in on a module that declares no pip. The opt-in
is signed into the layer, and `varve inspect` shows it (`--json` carries it as
`zephyr_allow_pip`). Zephyr's own build already needs *your* Python; that is
outside this.

See also: `varve docs inspect`, `varve docs payload-kinds`, `varve docs verify`.
